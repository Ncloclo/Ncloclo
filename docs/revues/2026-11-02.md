### Tests : un flake isolé, sans rapport avec l'argent

`python -m pytest tests -q -p no:cacheprovider` : **889 tests passent, 13
ignorés**, et un seul test échoue systématiquement en suite complète,
reproduit deux fois à l'identique :
`tests/test_real_conditions.py::test_stalled_cycle_dumps_thread_stacks`.
Ce test vérifie une fonctionnalité de diagnostic (l'écriture d'une pile de
threads dans `<journal>.blocage.txt` quand un cycle du bot reste bloqué
plus de 20 minutes en production, raccourci à 0,3 s pour le test) ajoutée
le 1ᵉʳ octobre — avant la dernière revue de code, donc pas une régression
de cette semaine.

J'ai vérifié avant de le signaler comme tel : il **passe toujours** seul,
dans son fichier seul, avec le fichier qui le précède dans la suite
(`test_process_lock.py`), et même sous charge CPU artificielle ; il
**échoue systématiquement** une fois inséré après l'essentiel de la suite
(reproduit avec 725 tests qui le précèdent comme avec 889). La cause est
donc liée à un état accumulé par l'ensemble de la suite (threads ou
minuteur du module `faulthandler`, utilisé une seule fois par processus),
pas à une logique d'achat, de risque ou de protection — cette
fonctionnalité n'écrit qu'un fichier de diagnostic, jamais consultée par
la porte d'exécution. Je n'ai pas corrigé ce flake cette semaine (la cause
exacte, probablement une interaction entre plusieurs tests qui arment la
même minuterie `faulthandler` sans la libérer, demande plus de temps que
cette revue ne peut en consacrer sans risquer un correctif hasardeux sur
un mécanisme de bas niveau) ; à surveiller si GitHub affiche ce même test
en rouge sur cette Pull Request — ce serait ce flake connu, pas un vrai
défaut, et relancer isolément ce test suffit à le confirmer :
`pytest tests/test_real_conditions.py::test_stalled_cycle_dumps_thread_stacks`.

`python -m ruff check .` : **aucune erreur**.
